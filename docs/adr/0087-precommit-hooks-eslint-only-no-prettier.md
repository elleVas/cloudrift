# ADR-0087: Pre-commit hooks via husky + lint-staged, `eslint --fix` only — no `prettier --write`

- **Status:** Accepted (2026-07-26)

## Context

Phase 7 of the 2026-07-25 code-review follow-up plan called for pre-commit hooks so lint problems are caught before they reach CI, on exactly the files being committed rather than the whole tree. The repo already has `prettier` (`^3.9.6`) and `eslint-config-prettier` as devDependencies, plus a root `.prettierrc` (`{ "singleQuote": true }`), which made "run Prettier in the hook too" the default first instinct.

Checking that instinct against the actual codebase surfaced a problem: the codebase is **not** Prettier-clean today. Existing files routinely exceed Prettier's default `printWidth: 80` (e.g. single-line object literals and Zod chains in `mcp.command.ts`, import lists in `aggregate-analysis.use-case.spec.ts`) and CI has no `prettier --check` step — `pnpm nx run-many -t lint` only runs ESLint, and `eslint-config-prettier` merely *disables* ESLint rules that would conflict with Prettier's formatting; it enforces nothing on its own. Running `prettier --write` against a real staged file during this work reformatted the entire file (wrapping every long line, not just the ones actually changed), producing a diff many times larger than the actual edit and full of unrelated churn.

## Decision

`husky` (git hook management, `prepare` script sets `core.hooksPath` on `pnpm install`) + `lint-staged` (runs configured commands only against staged files) are added as root devDependencies. `.husky/pre-commit` runs `pnpm exec lint-staged`; the root `package.json`'s `"lint-staged"` key maps `*.{ts,tsx,js,jsx}` to `eslint --fix` only:

```json
"lint-staged": {
  "*.{ts,tsx,js,jsx}": "eslint --fix"
}
```

No Prettier step is included. `.husky/_` (husky's internal helper directory, generated by `husky init`) is not tracked — it ships its own `.gitignore`, so only `.husky/pre-commit` (the one hook script this decision authored) is committed.

## Alternatives Considered

- **`eslint --fix` + `prettier --write` in the same hook.** Rejected for now: given the codebase isn't Prettier-formatted today, this would silently reformat every pre-existing line in any file a commit happens to touch, not just the lines that changed — a large, unrelated diff riding along with every future commit until the whole tree is reformatted once, deliberately, as its own change.
- **Reformat the whole repository with Prettier first, then wire it into the hook.** Not adopted here: a repo-wide reformat is its own reviewable change (large diff, worth doing deliberately and separately, likely with `git blame` implications the user should decide on) — out of scope for a "add pre-commit hooks" phase.
- **`nx affected -t lint` in the hook instead of `lint-staged` + plain `eslint`.** Rejected: `nx affected` reasons about project boundaries and would re-lint every file in any affected project, not just the staged ones — slower for a pre-commit hook, whose whole point is to be fast enough to run on every commit. Plain `eslint --fix` was verified to work standalone from the repo root against the flat config (`eslint.config.mjs`) without an Nx wrapper.
- **`husky install` classic API instead of `husky init` / v9's hookless model.** Not applicable: husky 9.x removed `husky install` and the old `.huskyrc` shim entirely: `pnpm exec husky init` is the only supported setup path for this version.

## Consequences

Verified end-to-end: staged a real file, ran `sh .husky/_/pre-commit` directly (the actual git-invoked script, without creating a commit), confirmed `eslint --fix` ran and re-staged its output, exit code 0. `pnpm install` alone is sufficient for a fresh clone to get the hook active (via the `prepare` script) — no manual `husky init` step for new contributors. `CONTRIBUTING.md` step 6 now mentions the hook, framed as a fast staged-files check, not a substitute for `pnpm nx affected -t lint,test,typecheck` (step 5).

Revisit if the codebase is ever reformatted to be Prettier-clean in one deliberate pass: at that point, adding `prettier --write` (or `--check`) to both the hook and CI becomes low-risk and this ADR's rejection of it no longer applies.
