# ADR-0101: `FindingConfidence` — real price differences replace heuristic fractions for rightsizing scanners

- **Status:** Accepted

## Context

Three `category: 'optimization'` scanners priced their finding as a flat fraction of an unrelated real number, with no connection to the actual resource: `ec2-underutilized`/`rds-underutilized` reported `instancePrice × 0.5` (`RIGHTSIZE_SAVING_FRACTION`) regardless of what a smaller instance actually costs, and `dynamodb-overprovisioned` reported `provisionedCost × 0.5` regardless of real consumed capacity. A fourth scanner, `s3-no-lifecycle`, reported `standardStorageCost × 0.4` — a number with an even weaker basis, since the real saving depends on the bucket's object-age distribution, which cloudrift has no way to observe (a backup bucket full of cold objects might save 80%; a bucket of daily-served assets could get *more* expensive moving to Infrequent Access). A fifth, `sagemaker-training-orphaned`, priced an orphaned model's S3 storage at a flat assumed 5GB, regardless of the model's real artifact size.

An external technical review (2026-08-01) singled these out specifically: two of the five (EC2/RDS rightsizing, DynamoDB) have a real, computable answer sitting in data cloudrift already collects (the Pricing API, CloudWatch consumed-capacity metrics) — reporting a blind percentage instead was leaving a better number on the table, not a necessary simplification. The other two (S3 lifecycle, SageMaker artifact size) have *no* real basis at all — a percentage of a percentage of an unknown. Showing a dollar figure for those isn't an imprecise estimate, it's a number invented to fill a column.

`aurora-serverless-overprovisioned` and `eks-node-overprovisioned` were checked against the same standard and found already correct: both price a real ACU-hour/instance-hour rate against a peak-derived (not flat-percentage) recommendation — see their scanners' `toEntity()`.

## Decision

**Two scanners get a real price subtraction instead of a fraction.** `ec2-underutilized`/`rds-underutilized` now compute one instance size down within the same family via a new pure helper, `stepDownOneSize()` (`libs/cloud-cost/infrastructure/aws-adapter/src/utils/instance-step-down.ts`): a canonical `nano…48xlarge` size-tier ordering, family prefix preserved (`m5.2xlarge` → `m5.xlarge`, `db.r5.large` → `db.r5.medium`), `.metal` sizes deliberately excluded (no fixed position across families, so no defensible "one step down"). Both the current and stepped-down type's price are resolved from the Pricing API; the saving is their real difference. `dynamodb-overprovisioned` computes a recommended RCU/WCU from the *average* consumed rate over the window (CloudWatch returns one aggregate `Sum` datapoint, not a time series — there is no real peak signal available without a bigger architectural change, see Alternatives) times a 3x headroom multiplier, floored at 1 unit and capped at the current allocation; the saving is the real RCU/WCU price difference.

**When no real number is derivable, `monthlyCostUsd` is `0`, never a fallback guess.** Already-smallest instance types, families where the Pricing API has no smaller-size entry, or a DynamoDB table whose average-derived recommendation isn't actually cheaper all report `$0` for that specific finding — the finding itself (and its non-monetary reasoning) still surfaces.

**`s3-no-lifecycle` and `sagemaker-training-orphaned` are zeroed out entirely**, dropping `ESTIMATED_SAVING_FRACTION`/`ASSUMED_MODEL_ARTIFACT_GB` — both now always report `monthlyCostUsd: 0` and read as pure hygiene flags ("no lifecycle policy configured — evaluate based on object age" / "orphaned, no dollar estimate"). Both scanners' now-unused `PricingPort` constructor dependency was removed rather than left dead.

**A new domain concept, `FindingConfidence` (`measured | derived | heuristic`), makes the distinction explicit and machine-readable**, orthogonal to the existing `FindingCategory`/`estimated` fields from [ADR-0015](0015-findingcategory-waste-vs-optimization.md) (kept unchanged, for output-shape compatibility — see Consequences):
- `measured`: real price × observed quantity. Every `category: 'waste'` kind, by that category's own definition.
- `derived`: real price *difference* between two real prices — the six kinds above (EC2/RDS/DynamoDB from this ADR, `ebs-gp2-upgrade`/`aurora-serverless-overprovisioned`/`eks-node-overprovisioned`, already real). Still advisory, still `category: 'optimization'`, still needs verifying — a real number doesn't mean the recommendation is safe to apply blindly.
- `heuristic`: no real dollar basis. `s3-no-lifecycle`, `lambda-underutilized` (already `$0`, unchanged), `sagemaker-training-orphaned`. Always `$0`.

`confidenceOf(kind)` (`libs/cloud-cost/domain/src/wasted-resource.ts`) computes this from `category` plus a small explicit `DERIVED_OPTIMIZATION_KINDS` set (6 of the 44 kinds) rather than a 44-entry per-kind field — every `waste` kind is `measured` by construction, so a per-kind literal would mean 35 entries all repeating the same value.

**Formatters (table/PDF/markdown) use `confidence` to change display, not gating.** A `heuristic` finding's cost cell reads "no $ basis" instead of a misleadingly-precise "$0.00/mo" (which would read as "confirmed no waste" rather than "we chose not to guess"). A `derived` finding is labeled `(derived)` in the breakdown. The waste/optimization headline totals are unchanged in *value* — `totalWasteMonthlyUsd` already summed exactly the `measured` kinds and `totalOptimizationMonthlyUsd` already summed exactly the `derived` kinds (since `heuristic` kinds always contribute `$0`) — only their on-screen labels changed, to "Total waste (measured)" / "+ $X/month derived (... not included in the total above)".

## Alternatives Considered

- **Fetch per-period CloudWatch datapoints for DynamoDB to get a real peak, instead of an average + margin.** Rejected for this pass: `GetMetricStatistics` caps at 1440 datapoints per call, so a 7-day window needs at least a 7-minute period to stay under that — deliverable, but it's a materially bigger change (new query shape, more data volume, a genuinely different `fetchMetric` contract) than the rest of this fix. The 3x-over-average multiplier is a documented, conservative stand-in, not a hidden assumption — revisit if real-world usage shows it's too aggressive or too conservative.
- **Replace `category`/`estimated` with `confidence` everywhere, including the JSON/CSV/MCP output shape.** Rejected: those fields are consumed by the DTO, the MCP tool schema, and CSV columns — output surfaces external tools/CI pipelines may already parse. Renaming or removing them is a breaking change to a public-ish contract, a separate decision from "fix the formulas." `confidence` was added *additively* instead.
- **Store `confidence` as a literal field per `RESOURCE_KIND_META` entry (44 entries), matching how `category`/`estimated`/`effort` are stored.** Rejected: 38 of 44 kinds are `measured` purely because they're `category: 'waste'` — a per-kind literal would be 38 lines of guaranteed-correct-by-construction duplication. The derived function plus a 6-name exception set is smaller and keeps the "which kinds are `derived`" answer in one place a reviewer can actually check.
- **Keep the S3/SageMaker heuristic fractions but only label them more visibly.** Considered first, rejected on reflection: labeling a number that has no real basis doesn't make it more honest, it just makes the invented number easier to find. `$0` plus a text reason is the correct floor for "we have no basis to price this."

## Consequences

`ec2-underutilized`/`rds-underutilized`/`dynamodb-overprovisioned` findings now show a real, per-resource dollar figure that varies with the actual instance type/table instead of a constant 50%-of-something; some findings within the same scan now legitimately show `$0` (already-smallest tier, no cheaper Pricing API entry) where before they'd have shown a nonzero guess. `s3-no-lifecycle` and `sagemaker-training-orphaned` always show `$0` now — a visible drop in `totalOptimizationMonthlyUsd` for existing users is expected and correct, not a regression. `totalWasteMonthlyUsd`/the CI gate are unaffected (both scanners were always `category: 'optimization'`, never gated). The DTO/MCP catalog gained an additive `confidence` field; existing consumers reading `category`/`estimated` see no change. Two contract fixtures (`dynamodb-overprovisioned.json`, `sagemaker-training-orphaned.json`) had their expected `monthlyCostUsd` recomputed to match; the EC2/RDS fixtures' expected values were unchanged by coincidence (the stub prices used for testing happen to make the old `×0.5` and the new real-subtraction formula agree numerically — real Pricing API data won't generally do that).
